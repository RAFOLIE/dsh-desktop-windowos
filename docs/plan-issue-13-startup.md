# Issue #13：冷启动等待与无副作用能力识别

状态：用户已批准执行。实现及验证记录见 `issue-13-startup-checks.md`；已纳入 v1.6.63 稳定版发布范围；未关闭 Issue。

Issue：https://github.com/RAFOLIE/dsh-desktop-windowos/issues/13

## 调查结论

1. **主因在当前 v1.6.52 仍存在。** `src-tauri/src/dsh.rs` 的 `GLOBAL_WINDOW` 是 30 秒；customDshPath、PATH 全局安装和本地安装都使用它。`try_candidate` 到期时直接 tree-kill，不以“仍存活”作为继续等待条件。Issue 报告的 41–60 秒冷启动会被中途终止。该耗时来自报告者，本轮未重启真实服务去复现。
2. **探针不是无副作用命令。** `web_help_mentions_no_open` 执行 `<dsh> web --help`，8 秒后强杀。本机日志同样记录该超时。已安装的官方 DSH 0.1.5-rc.2 CLI 会先进入 web profile 的 compose/依赖处理，再由 web-startup 提供帮助。
3. **锁风险有源码依据，但本机未证明发生同一次残留。** 官方 atomic-write 以排他创建的文件保存 PID，正常 finally 才清理；抢锁者超时失败，不自动回收已有锁。强杀绕过正常退出，确有遗留锁的机制风险。Issue 的锁时间线属于报告者证据，不能写作本机已复现。
4. **仅替换成顶层 `--help` 不完整。** 当前 CLI 顶层帮助不枚举 web 专属 `--no-open`。它能避开 profile 启动，但不能可靠替代该能力探测。
5. **还有两个配套问题。** 候选列表构建阶段就运行所有帮助探针，正式启动前可能累积多个 8 秒等待；`web_shortcut.rs` 另有独立 120 秒总等待，与多个候选及 npx 300 秒窗口不一致。

## 建议方案

### 1. 先用明确的等待上限修复误杀

- 已安装 DSH（自定义路径/PATH/本地）默认就绪窗口统一为 **120 秒**，与 DSH_CMD 一致；npx 保留 **300 秒**。
- 缺失命令、明确退出和明确错误仍及时结束当前尝试；不能因为窗口加长而把立即失败拖满 120 秒。
- 保留等待上限，第一版不采用“持续输出就无限延期”。持续输出可能只是报错或心跳，不能当作启动进展。
- 用可控测试时钟验证 41/60/119 秒就绪不被杀、到期仍不就绪进入明确失败。实际时限允许一次已在进行的有界就绪探测耗时，避免宣称精确毫秒终止。

### 2. 移除会启动 profile 的能力探针

- 候选发现只做路径/元数据读取，不执行 `web --help` 或其他会 compose profile 的命令。
- 对可解析的官方 npm/pnpm 安装，定位到实际包及 web 启动入口，通过经验证的包版本/参数定义判定 `--no-open`，不能只看某个同名 PATH 命令或粗略比较“新旧版”。
- 将支持/不支持/未知分开。路径、包装脚本或源码版本无法确认时，不启动潜在有副作用的探针；未知时采用兼容回退并说明可能由 DSH 自行打开浏览器，不能让未知参数阻止正式启动。
- 用户提供的完整 DSH_CMD 保持原样；自定义包装脚本不擅自改写。能力缓存绑定实际包来源与版本/文件变化，升级后失效。
- 可证明指向同一启动目标和工作目录的重复候选去重；无法证明的包装器保留既有优先级。

### 3. 启动状态和网页入口使用同一生命周期

- 提供候选、阶段、已用时间、预算及明确的提前退出/等待超时信息；启动较慢时继续展示“正在启动”，不能静默换候选。
- `web_shortcut.rs` 跟随启动生命周期，而非无条件在 120 秒时先宣布失败；仍设置有界的总体等待与取消条件，避免永久挂起。
- 核对普通启动、手动重启、内核更新后的重启及现有服务附加。已有服务附加不运行探针、不新增实例，也不扩大进程清理范围。

### 4. 明确处理已存在的 writer lock 错误

- 准确识别 `timed out waiting for the writer lock`，显示锁路径及可核验的占用状态，避免静默换几个等价候选重复争锁。
- 不以“文件够旧”自动删除锁，不修改官方包、不清空 profile 或会话数据。
- 对已有残留锁给出操作指引；必须确认相关写入活动停止后才能恢复，不在本轮调查期间操作用户锁文件。此项与防止探针新造残留分开验收。

### 5. 验证与交付

| 用例 | 预期 |
|---|---|
| 41–60 秒冷启动 | 保持当前候选，成功就绪 |
| 命令缺失/进程提前退出 | 立即反馈实际失败，不空等 |
| 真正超过启动上限 | 明确说明超时；只清理拥有的候选进程 |
| 支持/不支持/未知 --no-open | 正确添加或保守回退，不启动 web profile 探针 |
| 连续冷启动 | 能力检查不新增或遗留 writer lock |
| 锁被活跃进程占用 | 不删除锁、不杀外部进程，显示明确诊断 |
| 已启动的终端 DSH | 直接复用，无重复启动 |
| 网页快捷方式等待慢启动/npx | 与启动阶段一致，不提前虚报失败 |
| 升级后重启 | 等待新版本就绪并保留既有来源/版本复核 |

单元测试和隔离临时 profile/伪 CLI 验证优先，不对用户现有服务执行强杀实验。编译后检查真实发行 exe 的版本资源与内嵌前端，实际点验后同步本地安装目录并保留备份。后续发布遵循既有版本流程；此次批准计划本身不代表现在已完成修复或可以关闭 Issue。
